# WildTrack - Sistema de Seguimiento de Fauna Silvestre

## Overview
WildTrack is a comprehensive wildlife tracking system designed to monitor animal studies by integrating with the Movebank API. It provides robust capabilities for data visualization, event detection, geospatial analysis, and automated alerting for various animal behaviors and statuses. The project aims to offer researchers a powerful tool for managing and analyzing wildlife movement data, enhancing ecological studies and conservation efforts.

## System Architecture
The system is built on a modern full-stack architecture. The frontend uses React with TypeScript, Tailwind CSS, Shadcn UI for components, Recharts for data visualization, and Leaflet for interactive maps. The backend is an Express application written in TypeScript, handling API requests, authentication, and business logic. PostgreSQL serves as the primary database, managed with Drizzle ORM. Authentication is implemented using Passport.js with local strategy and session management.

Key architectural features include:
- **Role-Based Access Control**: Three distinct user roles (superuser, user, observer) with granular permissions.
- **Data Synchronization**: Integration with the Movebank API for fetching individual and deployment data, with local caching in PostgreSQL for performance and offline access.
- **Event Detection System**: Server-side analysis of accelerometer data to identify specific animal behaviors (mortality, detachment, fight/predation, feeding, incubation/flight) based on configurable species profiles.
- **ACC Low Activity & Electrocution (Ornitela-only)**: Detectores adicionales en `server/eventDetection.ts` que solo se ejecutan cuando `study.ornitelaEnabled===true` (gate vía `options.ornitelaOnly` en `detectEvents`). Dispositivos sin datos ACC (`accSamples.length===0`) salen silenciosamente sin error.
  - **low_activity**: ventana deslizante con duración mínima 2 h (`thresholds.lowActivity.durationHours`, validada `min(2)`). Varianza combinada `xVar+yVar+zVar`: `<criticalCombinedVariance` (default 5) → severidad `critical` ("posible mortalidad"); `<warningCombinedVariance` (default 30) → `warning` ("posible animal herido"). Persiste `metadata={combined_variance, x/y/z_variance, duration_hours, samples}`. Nuevo `EventType="low_activity"` con color `#eab308`, severidad por defecto `warning`, label "Baja actividad ACC".
  - **electrocution**: busca `|dZ| ≥ zStepThreshold` (default 200) entre muestras consecutivas; recoge la ventana de `durationMinutes` (validada `min(30)`, default 30) tras el salto y exige: (a) `var(Z) < sustainedVariance` (default 5), (b) `|mean(Z pre) − mean(Z post)| ≥ zStepThreshold` (cambio permanente, no outlier), (c) `var(X) < 2×sustainedVar` y `var(Y) < 2×sustainedVar` (estabilidad multieje para descartar aterrizajes/golpes). Persiste `metadata={z_step, z_pre_mean, z_post_mean, z_variance_after, x/y_variance_after, duration_minutes, samples}`. Nuevo `EventType="electrocution"` con color `#b91c1c`, severidad `critical`, label "Posible electrocución".
  - **Dedupe 24h y precedencia**: en `server/scheduler.ts` (cron `runEventDetection`) y `server/routes.ts` (endpoint manual `POST /api/studies/:id/detect-events`), antes de persistir un `low_activity` o `electrocution` se consulta `findRecentUnresolvedDetectedEvent(studyId, animal, eventType, now-24h)` y se descarta el evento si hay uno reciente abierto. Además, para `low_activity` se suprime si existe un `mortality` abierto reciente para el mismo animal (precedencia semántica). Las alertas críticas siguen enviando email vía `sendEventAlert` con la dedup de `getAlertLog/createAlertLog` ya existente.
  - Umbrales nuevos añadidos a `eventThresholdsSchema`, `DEFAULT_THRESHOLDS` y `normalizeThresholds` en `shared/schema.ts` (perfiles antiguos heredan defaults automáticamente).
- **Configuración global**: Nueva tabla `app_settings` (key/value) con storage `getSetting/setSetting`. Primer ajuste: `no_transmission_threshold_days` (default 7, opciones 5/10/15/20) configurable desde `/admin/alerts` (página `client/src/pages/admin-alerts.tsx`, ruta restringida a superuser, link en sidebar). Endpoints `GET /api/admin/settings/no-transmission-threshold-days` (cualquier rol auth) y `PUT` (superuser).
- **Immobility/Mortality Detection**: GPS-based analysis for detecting prolonged immobility or lack of transmission, with configurable thresholds. El umbral `noTransmissionThresholdHours` toma como default `getNoTransmissionThresholdDays() * 24` leído de `app_settings` (override por request body sigue activo en `/api/studies/:id/immobility-analysis`). Las alertas `no_transmission` SOLO se generan para estudios con `ornitelaEnabled=true` (Movebank tiene ciclos de transmisión muy variables — días/semanas — que producían cientos de falsos positivos). El detector compara `now - lastGpsEvent.timestamp >= threshold` contra la última posición GPS real en `cached_gps_events`, no contra un ciclo esperado. Defaults: 96h ventana de análisis, 24h umbral inmovilidad, 48h umbral sin transmisión. Cron dedicado `*/5 * * * *` (`IMMOBILITY_CRON_INTERVAL`) ejecuta el chequeo cada 5 min sobre todos los estudios activos (necesario para detectar a tiempo la nueva alerta `zone_deviation`; el cron mantiene el mutex single-flight `immobilityCheckRunning` para evitar overlaps). **Filtro de exclusión**: animales sin histórico GPS (`getCachedTimestampRange` devuelve null → equivalente a `last_transmission=NULL`) se descartan del análisis y de las alertas. **Persistencia**: cada análisis (manual o cron) guarda en `detected_events` los eventos `mortality` (inmovilidad) y `no_transmission` (nuevo `EventType` añadido a `EVENT_TYPES`/`EVENT_LABELS`/`EVENT_COLORS`/`EVENT_SEVERITY`) con dedupe por ventana 24h vía `findRecentUnresolvedDetectedEvent(studyId, individualLocalId, eventType, sinceCreatedAtMs)`. **Resolución automática**: cuando un animal vuelve a transmitir (entra en `activeAnimals`), `markDetectedEventsResolved` marca `resolvedStatus=true` para sus eventos abiertos de `mortality`/`no_transmission`. **Email crítico**: el cron agrega las `newCriticalAlerts` (no dedupeadas) de todos los estudios y envía un único correo a `IMMOBILITY_ALERT_EMAIL` (default `jjiglesias@grefa.org`) vía `sendCriticalImmobilityEmail` con asunto `[WildTrack] ⚠️ X animales sin transmisión - {fecha}`, incluyendo animal/especie/estudio/tipo/horas/km fuera de zona/última transmisión/link Google Maps. La firma de `analyzeImmobility` admite `options.persist` (default `true`) por si se necesita ejecutar sin escribir.
- **Zone Deviation Detection (Ornitela-only)**: Para estudios con `ornitelaEnabled=true`, el detector calcula un radio dinámico por animal a partir del centroide y percentil 95 de distancias de los GPS de los últimos 30 días (mínimo 5 km, animales con <7 días de histórico se excluyen) usando `@turf/turf`. Si el último GPS está fuera del radio, se carga el ACC de las últimas 2 h y se promedia `|yAcceleration|`: actividad >150 → severidad `warning`, <30 → `critical`, sin datos ACC → `warning`. Los eventos se persisten como `zone_deviation` (nuevo `EventType` con color `#a855f7` y severidad por defecto `warning`) en `detected_events` con dedup 24 h vía `findRecentUnresolvedDetectedEvent`, guardando en la nueva columna `metadata jsonb` el JSON `{ km_outside, dynamic_radius_km, centroid_lat, centroid_lng, acc_activity_y, acc_samples }`. Auto-resolución: animales que vuelven dentro del radio en el siguiente análisis (no aparecen en `zoneDeviationAlerts`) se marcan `resolvedStatus=true` para sus `zone_deviation` abiertos. Las alertas críticas de zona se incluyen en `newCriticalAlerts` y en el email agregado, que ahora muestra una columna "Km fuera de zona". UI en `/immobility` añade tarjeta morada "Desviación de zona" con tabla (animal, km fuera, radio habitual, actividad ACC, severidad, link Google Maps) y marcadores morados en el mapa.
- **Geospatial Analysis Engine**: Utilizes Turf.js for advanced home range analysis (MCP, Kernel density), distance traveled, and movement speed calculations, with comprehensive visualization and export options.
- **Alerting System**: Automated email notifications for critical events, immobility, and emission monitoring, with deduplication.
- **Data Import**: Support for importing CSV data from various sources (Movebank, Base Lunar, Ornitela) with format auto-detection and intelligent parsing. CSV-imported individuals receive unique negative `movebankId` values to avoid unique-constraint conflicts. Post-import cache invalidation refreshes individuals, GPS counts, and last-positions views. GPS event count column ("Eventos GPS") displayed in study-detail individuals table via `GET /api/studies/:id/gps-counts`.
- **Data Caching Strategy**: A cache-first approach for GPS and accelerometer data, including explicit range tracking and gap-filling to optimize Movebank API calls.
- **GPS Quality Filter (HDOP)**: Los CSVs Ornitela incluyen columna `hdop` (Horizontal Dilution of Precision). El parser (`server/ornitelaCsvParser.ts`) detecta `findCol("hdop","h_dop","gps_hdop","horizontal_dop")` y la persiste en la nueva columna `cached_gps_events.hdop` (`doublePrecision`, nullable; Movebank inserta `null`). Constante `HDOP_QUALITY_THRESHOLD=5` en `shared/schema.ts`. **Detección de alertas**: `getLatestCachedGpsEvent` (storage) ya filtra `hdop IS NULL OR hdop <= 5` en SQL para "última posición válida"; en `server/immobilityDetector.ts` un helper `filterHighQualityGps` excluye HDOP>5 de `analyzeImmobility` (mortality/no_transmission, línea ~435) y del cálculo del radio dinámico de `zone_deviation` (línea ~642). Movebank y otros sin HDOP no se ven afectados (NULL acepta). **Mapas**: tanto `last-positions.tsx` (marcador final del animal) como `study-visualization.tsx` (trayectoria histórica) renderizan puntos con HDOP>5 en gris `#9ca3af` con `dashArray` y opacidad reducida, y muestran "HDOP: x.x (baja calidad)" en el popup. Los puntos NO se eliminan, solo se diferencian visualmente.
- **Credential Security**: Encryption of sensitive external credentials (e.g., Movebank) at rest using AES-256-GCM.
- **Ornitela Panel Sync**: Automated synchronization with Ornitela cpanel (login, HTML parsing with cheerio, CSV download per device IMEI) with configurable intervals and cron integration. The manual endpoint `POST /api/studies/:id/ornitela-sync` (superuser) streams progress over Server-Sent Events with a hard cap of 50 devices per call (`maxDevices`, `startIndex` for pagination); events: `login`, `start`, `device`, `done`, `error`. Frontend in `study-detail.tsx` loops batches automatically until `hasMore=false`, showing live `processed/total · GPS · ACC · current device` progress. This avoids the HTTP timeout that broke single-shot syncs with 200+ devices.
- **Scheduled Deployment Trigger**: `scripts/cron-sync.mjs` is a standalone Node script intended to be deployed as a Replit Scheduled Deployment (separate from the Autoscale web). It POSTs to `/api/sync-all` with `X-Sync-Secret` header every 6 hours, forcing event detection, emission check, and Ornitela sync independently of in-process node-cron (which can be killed when Autoscale instances scale to zero). El bundle `/api/sync-all` NO incluye `immobility_check`: ese chequeo tiene su propio cron de 2h (`IMMOBILITY_CRON_INTERVAL`) con mutex single-flight (`immobilityCheckRunning`) para evitar overlaps en horas alineadas y emails duplicados de "nuevas" alertas críticas. Required env vars: `SYNC_URL` (e.g. `https://wildtrack.replit.app/api/sync-all`) and `SYNC_SECRET`. Suggested cron schedule: `0 */6 * * *`.
- **Movebank Rate Limiting**: Singleton rate limiter (`server/movebankRateLimit.ts`) tracks daily request count (100/day limit, resets at UTC midnight), detects HTTP 429 responses (triggers 2-hour cooldown), and enforces 2-second delays between sequential Movebank API calls. The dashboard shows a real-time request counter, and sync buttons are disabled when blocked. Cron jobs skip Movebank calls when rate-limited.
- **Incremental Backfill of GPS/ACC**: The cron `runEventDetection` performs incremental backfill per animal/sensor using `getCachedTimestampRange` (max+1 ms → now, capped at 30 days). `recordFetchedRange` validates inputs (rejects ranges with `rangeStart < 1e12 ms` or `rangeEnd <= rangeStart`) to prevent garbage rows. The cron persists a dedicated `movebank_sync` entry in `cron_logs` with status `success | partial | error` summarizing studies/animals/GPS/ACC counts and whether it was cut short by the rate limiter. A manual endpoint `POST /api/studies/:id/backfill` (superuser) streams progress over Server-Sent Events with a 90-day cap; events: `start`, `animal`, `animal-error`, `rate-limit`, `done`, `error`. Detection of 429 uses `MovebankError.statusCode === 429` (not text matching). The "Sincronizar datos GPS" button on the study detail page consumes the SSE stream and surfaces live progress.
- **Automated Scheduling**: Cron jobs manage periodic tasks like event detection, emission checks, immobility analysis, and Ornitela sync.
- **Post-Sync Alert Trigger**: Tras cada sync de Movebank que persista nuevos GPS/ACC en `cached_*_events`, se dispara automáticamente `analyzeImmobility(studyId)` en background (`triggerImmobilityAnalysisInBackground` en `server/immobilityDetector.ts`, vía `setImmediate`, fire-and-forget) para evaluar `mortality`, `no_transmission` y `zone_deviation` con la misma lógica del cron y persistirlos en `detected_events`. Hook activo en: (a) cron `runEventDetection` de `server/scheduler.ts` (un Set `studiesWithNewData` agrega los studyIds tras cada `insertCachedGpsEvents`/`insertCachedAccEvents`, dispara una vez por estudio al terminar el bucle), y (b) endpoint manual `POST /api/studies/:id/backfill` SSE en `server/routes.ts` (dispara una vez al cierre del lote si `totalGps>0 || totalAcc>0`). El sync no se ralentiza porque la llamada se desacopla con `setImmediate` y los errores se loguean sin propagarse. La dedupe 24h de `findRecentUnresolvedDetectedEvent` evita duplicados con el cron de inmovilidad de 30 min.
- **Ornitela SFTP Watcher**: Background service (`server/services/sftpWatcher.ts`, started in `server/index.ts`) que se conecta cada 2 min vía SFTP a `146.148.12.195:22` (user `ornitela`, password en secret `ORNITELA_SFTP_PASSWORD`), lista CSVs en `/uploads`, los importa con el mismo `parseOrnitelaCsv` (rellena `cached_gps_events` y `cached_acc_events`, no hay tabla `location_events`), los mueve a `/uploads/processed` y registra cada filename en la tabla `processed_sftp_files` (UNIQUE) para evitar reprocesado. Resolución de `studyId` por archivo: lee `device_id` (primeras 10 filas, parser CSV robusto con soporte BOM/comillas) → `deployments.localIdentifier` → único study con `ornitelaEnabled+active` → `ORNITELA_DEFAULT_STUDY_ID` → null. Concurrencia protegida con mutex `isRunning`, retries 3× con backoff exponencial, primer tick a los 10s del arranque. Endpoints: `GET /api/sftp/status` (auth) devuelve estado completo (host, lastRunAt, lastError, recentErrors, recentFiles, totales) y `POST /api/sftp/run-now` (superuser) ejecuta un tick inmediato (responde 502 si hubo `globalError`, 409 si ya hay ejecución en curso). Variables opcionales: `ORNITELA_SFTP_HOST/PORT/USER/REMOTE_DIR/POLL_MS/DISABLED`, `ORNITELA_DEFAULT_STUDY_ID`.
- **Reference Data System**: Species catalog (`species` table: id, nombre_comun, nombre_cientifico) and Projects catalog (`projects` table: id, descripcion, id_especie FK). Individuals can be assigned to a project (`project_id` FK) and given a `history_number`. Seed data import endpoint (`POST /api/admin/import-reference-data`) loads 31 species and 61 projects idempotently. Admin pages at `/admin/ref-species` and `/admin/ref-projects` with full CRUD.
- **Individual Project Assignment**: Edit dialog on study-detail includes Proyecto dropdown and Nº Historial field. History numbers render as external links to `http://192.168.2.1/buho/formulario_historiales.php?editar_exp={history_number}`. Project and Nº Historial columns added to the individuals table.
- **Project Filtering**: All animal-listing pages (study-detail, geo-analysis, study-visualization, last-positions) include a project filter dropdown that appears when any individuals in the current context have projects assigned. The filter narrows the displayed/selectable animals to those belonging to the chosen project.
- **Notification Bell**: Componente `NotificationBell` en `client/src/components/notification-bell.tsx`, montado en el header global de `client/src/App.tsx` junto al `ThemeToggle`. Muestra icono `Bell` (lucide-react) con badge destructivo del conteo de alertas no leídas (`readStatus=false`). Al abrir, despliega un `Popover` con las últimas 15 alertas: tipo (color/label desde `EVENT_COLORS`/`EVENT_LABELS`), animal, descripción, severidad y "hace X min". Acciones: marcar individual (`POST /api/alerts/:id/read`), marcar todas (`PATCH /api/alerts/bulk/read`) y enlace a `/alerts`. Polling cada 30s vía `refetchInterval` + `refetchOnWindowFocus`; al mutar se invalidan `/api/alerts/history` y `/api/dashboard/summary`. Fuente de datos: `GET /api/alerts/history?readStatus=false&limit=15` (con scoping por permisos de usuario ya implementado en routes.ts).
- **UI/UX**: Features a dark/light theme toggle, collapsible sidebar, interactive charts and maps with bidirectional synchronization, and intuitive admin interfaces for managing studies, users, species profiles, species catalog, and projects.

## External Dependencies
- **Movebank API**: Primary source for animal tracking data (individuals, deployments, GPS/accelerometer events).
- **PostgreSQL**: Relational database for all application data, cached Movebank data, and session storage.
- **Nodemailer**: Used for sending email alerts and notifications via SMTP.
- **Google Maps**: Links provided in event alerts for easy location viewing.
- **Turf.js**: JavaScript library for advanced geospatial analysis.
- **Ornitela**: Integration for syncing device data from Ornitela panels via HTML parsing and CSV import.
