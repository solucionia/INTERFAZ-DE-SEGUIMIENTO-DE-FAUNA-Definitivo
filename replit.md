# WildTrack - Sistema de Seguimiento de Fauna Silvestre

## Overview
WildTrack is a comprehensive wildlife tracking system designed to monitor animal studies by integrating with the Movebank API and Ornitela devices. It provides data visualization, event detection, geospatial analysis, and automated alerting for animal behaviors and statuses, helping researchers manage and analyze wildlife movement data for ecological studies and conservation.

## User Preferences
- Language: Spanish (UI text in Spanish)
- Dark theme by default
- Scientific/technical design aesthetic

## Arquitectura

### Stack
- **Frontend**: React + TypeScript, Tailwind CSS, Shadcn UI, Recharts (gráficas), Leaflet (mapas). Routing con wouter, datos con TanStack Query.
- **Backend**: Express en TypeScript. Autenticación con Passport.js (estrategia local) + gestión de sesión.
- **Base de datos**: PostgreSQL gestionada con Drizzle ORM. Almacena datos de la app, caché de Movebank/Ornitela y sesiones.
- **Separación dev/prod**: la base de datos de desarrollo (Replit Helium) y la de producción (Neon) son instancias **distintas**. Un cambio en dev no afecta a prod y viceversa; hay que aplicar migraciones/datos en cada entorno por separado.

### Configuración global
- **`app_settings`**: tabla key/value con storage `getSetting/setSetting`. Primer ajuste: `no_transmission_threshold_days` (default 7, opciones 5/10/15/20) configurable desde `/admin/alerts` (`client/src/pages/admin-alerts.tsx`, superuser, link en sidebar). Endpoints `GET /api/admin/settings/no-transmission-threshold-days` (cualquier rol auth) y `PUT` (superuser).

### Acceso y roles
- **Role-Based Access Control**: tres roles (superuser, user, observer) con permisos granulares. El scoping por permisos se aplica en `routes.ts` (p. ej. `getStudiesForUser`).
- **Estado activo/inactivo de animales**: columna `individuals.is_active` (boolean, default true). Endpoint `PATCH /api/individuals/:id/active-status` (superuser). Un animal inactivo NO genera alertas nuevas: se excluye del cron de detección, del chequeo de emisión (`getActiveStudiesWithDeployments` devuelve `isActive` por animal), de `analyzeImmobility` (mortality/no_transmission/zone_deviation) y del endpoint manual `detect-events` (el set de inactivos incluye `localIdentifier` e `id` UUID por animales transferidos). El historial sigue visible y el sync continúa. `upsertIndividuals` no toca `is_active` en conflicto, así que los syncs de Movebank preservan el flag. UI en `study-detail.tsx`: badge "Inactivo — sin alertas" y botón Power/PowerOff (superuser) con confirmación.

### Datos de referencia y proyectos
- **Reference Data System**: catálogo de especies (`species`: id, nombre_comun, nombre_cientifico) y de proyectos (`projects`: id, descripcion, id_especie FK). Los individuos se asignan a un proyecto (`project_id` FK) y a un `history_number`. Seed idempotente vía `POST /api/admin/import-reference-data` (31 especies, 61 proyectos). Admin CRUD en `/admin/ref-species` y `/admin/ref-projects`.
- **Individual Project Assignment**: el diálogo de edición en study-detail incluye dropdown Proyecto y campo Nº Historial. Los Nº Historial se renderizan como enlaces externos a `http://192.168.2.1/buho/formulario_historiales.php?editar_exp={history_number}`. Columnas Proyecto y Nº Historial en la tabla de individuos.
- **Project Filtering**: todas las páginas de listado de animales (study-detail, geo-analysis, study-visualization, last-positions) muestran un dropdown de filtro por proyecto cuando algún individuo del contexto tiene proyecto asignado.

### UI/UX
- Toggle de tema claro/oscuro, sidebar colapsable, gráficas y mapas interactivos con sincronización bidireccional, e interfaces de admin para estudios, usuarios, perfiles de especie, catálogo de especies y proyectos.
- **Notification Bell** (`client/src/components/notification-bell.tsx`, montado en el header global de `App.tsx` junto a `ThemeToggle`): icono `Bell` con badge del conteo de alertas no leídas (`readStatus=false`). Acciones: marcar individual (`POST /api/alerts/:id/read`), marcar todas (`PATCH /api/alerts/bulk/read`), enlace a `/alerts`. ## Integraciones

### Movebank API
Fuente primaria de datos de seguimiento (individuos, deployments, eventos GPS/acelerómetro), con caché local en PostgreSQL para rendimiento y acceso offline.
- **Rate Limiting** (`server/movebankRateLimit.ts`, singleton): límite de 100 peticiones/día (reset a medianoche UTC), detecta HTTP 429 (cooldown de 2h) y fuerza 2s entre llamadas secuenciales. El dashboard muestra el contador en tiempo real y deshabilita los botones de sync cuando está bloqueado; los crons omiten llamadas a Movebank si hay rate-limit. La detección de 429 usa `MovebankError.statusCode === 429` (no coincidencia de texto).
- **Incremental Backfill GPS/ACC**: el cron `runEventDetection` hace backfill incremental por animal/sensor vía `getCachedTimestampRange` (max+1 ms → now, tope 30 días). `recordFetchedRange` valida entradas (rechaza `rangeStart < 1e12 ms` o `rangeEnd <= rangeStart`) para evitar filas basura. El cron persiste una entrada `movebank_sync` en `cron_logs` (status `success | partial | error`) resumiendo estudios/animales/GPS/ACC y si lo cortó el rate limiter. Endpoint manual `POST /api/studies/:id/backfill` (superuser) hace streaming SSE con tope de 90 días; eventos: `start`, `animal`, `animal-error`, `rate-limit`, `done`, `error`. El botón "Sincronizar datos GPS" de study-detail consume el SSE.

### Ornitela
Sincronización de datos de dispositivos Ornitela por dos vías: panel cpanel (HTML) y SFTP.
- **Panel Sync**: login + parseo HTML con cheerio + descarga de CSV por IMEI, con intervalos configurables e integración cron. Endpoint manual `POST /api/studies/:id/ornitela-sync` (superuser) hace streaming SSE con tope de 50 dispositivos por llamada (`maxDevices`, `startIndex` para paginar); eventos: `login`, `start`, `device`, `done`, `error`. El frontend (`study-detail.tsx`) itera batches hasta `hasMore=false` mostrando `processed/total · GPS · ACC · dispositivo actual`. **Por qué**: evita el timeout HTTP que rompía los syncs de un solo tiro con 200+ dispositivos.
- **SFTP Watcher** (`server/services/sftpWatcher.ts`, arrancado en `server/index.ts`): cada 2 min se conecta vía SFTP a `146.148.12.195:22` (user `ornitela`, password en secret `ORNITELA_SFTP_PASSWORD`), lista CSVs en `/uploads`, los importa con `parseOrnitelaCsv` (rellena `cached_gps_events` y `cached_acc_events`; no hay tabla `location_events`), los mueve a `/uploads/processed` y registra cada filename en `processed_sftp_files` (UNIQUE) para no reprocesar. Resolución de `studyId` por archivo: `device_id` (primeras 10 filas, parser CSV robusto con BOM/comillas) → `deployments.localIdentifier` → único study con `ornitelaEnabled+active` → `ORNITELA_DEFAULT_STUDY_ID` → null. Mutex `isRunning`, retries 3× con backoff exponencial, primer tick a los 10s. Endpoints: `GET /api/sftp/status` (auth) y `POST /api/sftp/run-now` (superuser; 502 si `globalError`, 409 si ya hay ejecución en curso). **Por qué se deshabilita en dev**: el watcher **mueve** cada archivo a `/uploads/processed` tras importarlo, así que el primer entorno que hace poll consume el archivo y el otro no lo ve nunca. Como dev y prod usan bases de datos distintas, un watcher en dev desviaría telemetría de producción. Por eso se mantiene `ORNITELA_SFTP_DISABLED=1` **solo en desarrollo**; sólo el deployment publicado debe consumir el feed.
- **Ornitela Name Display (backend)**: columna `individuals.ornitela_name` (nullable) que persiste el nombre del dispositivo tal como aparece en el HTML de cpanel.glosendas.net (no viene del CSV, sólo del scrape). `parseOrnitelaCsv` acepta `options.ornitelaName` y lo guarda vía `storage.updateIndividualOrnitelaName` (filtra placeholders `/^Device-[A-Za-z0-9]+$/`, sólo actualiza si cambió). `routes.ts` pasa `device.name` desde el sync por panel; el SFTP watcher no aporta nombre.

### Otras dependencias externas

- **Google Maps**: enlaces en las alertas para ver la localización.

## Detección de eventos y alertas

### Event Detection base
Análisis server-side de datos de acelerómetro para identificar comportamientos (mortality, detachment, fight/predation, feeding, incubation/flight) según perfiles de especie configurables.

### ACC Low Activity & Electrocution (solo Ornitela)
Detectores en `server/eventDetection.ts` que sólo corren cuando `study.ornitelaEnabled===true` (gate vía `options.ornitelaOnly` en `detectEvents`). Dispositivos sin datos ACC (`accSamples.length===0`) salen silenciosamente.
- **low_activity**: ventana deslizante, duración mínima 2 h (`thresholds.lowActivity.durationHours`, validada `min(2)`). Varianza combinada `xVar+yVar+zVar`: `<criticalCombinedVariance` (default 5) → `critical` ("posible mortalidad"); `<warningCombinedVariance` (default 30) → `warning` ("posible animal herido"). Persiste `metadata={combined_variance, x/y/z_variance, duration_hours, samples}`. `EventType="low_activity"`, color `#eab308`, severidad default `warning`, label "Baja actividad ACC".
- **electrocution**: busca `|dZ| ≥ zStepThreshold` (default 200) entre muestras consecutivas; toma la ventana de `durationMinutes` (validada `min(30)`, default 30) tras el salto y exige: (a) `var(Z) < sustainedVariance` (default 5), (b) `|mean(Z pre) − mean(Z post)| ≥ zStepThreshold` (cambio permanente, no outlier), (c) `var(X) < 2×sustainedVar` y `var(Y) < 2×sustainedVar` (estabilidad multieje para descartar aterrizajes/golpes). Persiste `metadata={z_step, z_pre_mean, z_post_mean, z_variance_after, x/y_variance_after, duration_minutes, samples}`. `EventType="electrocution"`, color `#b91c1c`, severidad `critical`, label "Posible electrocución".
- **Dedupe 24h y precedencia**: en `server/scheduler.ts` (`runEventDetection`) y `server/routes.ts` (`POST /api/studies/:id/detect-events`), antes de persistir un `low_activity`/`electrocution` se consulta `findRecentUnresolvedDetectedEvent(studyId, animal, eventType, now-24h)` y se descarta si hay uno reciente abierto. Además, `low_activity` se suprime si existe un `mortality` abierto reciente para el mismo animal (precedencia semántica). Las alertas críticas envían email vía `sendEventAlert` con la dedup de `getAlertLog/createAlertLog`.
- Umbrales añadidos a `eventThresholdsSchema`, `DEFAULT_THRESHOLDS` y `normalizeThresholds` en `shared/schema.ts` (perfiles antiguos heredan defaults automáticamente).

### Immobility / Mortality Detection
`server/immobilityDetector.ts` (`buildMortalityAlert`).
- **Criterio PRINCIPAL = acelerómetro** (`detectAccMortality`): ventana de las últimas `immobilityThresholdHours` (default 24h) hasta `now`; exige `>=accMinSamples` (default 10), cobertura `span>=90%` de la ventana y sin huecos >50% (`maxGap`/`MAX_GAP_FRACTION`); varianza combinada `var(x)+var(y)+var(z)`: `<accVarianceThreshold` (default 5) → `status="dead"` (`method="acc"`); `>=` → `status="alive"`.
- **Guard anti-falsos-positivos de incubación**: si el ACC dice "alive" NO se genera alerta y NO se cae a GPS. **Por qué**: un animal incubando está quieto pero su ACC tiene actividad → "alive".
- **Criterio SECUNDARIO = GPS por radio** (`detectGpsRadiusMortality`), SÓLO cuando el ACC es inconcluyente (sin datos): centro mediano (robusto a outliers), inmóvil si el percentil 90 de distancias cae dentro de `immobilityRadiusMeters` (default 50m), ignorando hasta un 10% de outliers.
- Campos configurables en `ImmobilityConfig`/`DEFAULT_IMMOBILITY_CONFIG` (`accVarianceThreshold`, `accMinSamples`, `immobilityRadiusMeters`), expuestos en `POST /api/studies/:id/immobility-analysis`. La carga usa `max(hoursToAnalyze, immobilityThresholdHours)`. `ImmobilityAlert` lleva `method:"acc"|"gps"` y `accVariance`; la UI `/immobility` muestra columna "Método". El evento `mortality` persiste `metadata={method, acc_combined_variance, duration_hours, samples}`.
- **no_transmission**: default de `noTransmissionThresholdHours` = `getNoTransmissionThresholdDays() * 24` leído de `app_settings` (override por request body activo en `/api/studies/:id/immobility-analysis`). SÓLO se generan para estudios con `ornitelaEnabled=true`. **Por qué**: Movebank tiene ciclos de transmisión muy variables (días/semanas) que producían cientos de falsos positivos. Compara `now - lastGpsEvent.timestamp >= threshold` contra la última posición GPS real en `cached_gps_events`. Defaults: 96h ventana de análisis, 24h umbral inmovilidad, 48h umbral sin transmisión.
- **Filtro de exclusión**: animales sin histórico GPS (`getCachedTimestampRange` → null, equivalente a `last_transmission=NULL`) se descartan del análisis y de las alertas.
- **Persistencia + resolución**: cada análisis (manual o cron) guarda en `detected_events` los `mortality` y `no_transmission` con dedupe 24h vía `findRecentUnresolvedDetectedEvent`. Cuando un animal vuelve a transmitir (entra en `activeAnimals`), `markDetectedEventsResolved` marca `resolvedStatus=true` para sus eventos abiertos.
- **Email crítico**: el cron agrega las `newCriticalAlerts` (no dedupeadas) de todos los estudios y envía un único correo a `IMMOBILITY_ALERT_EMAIL` (default `jjiglesias@grefa.org`) vía `sendCriticalImmobilityEmail`, asunto `[WildTrack] ⚠️ X animales sin transmisión - {fecha}`. `analyzeImmobility` admite `options.persist` (default `true`).
- **Cron dedicado**: `*/5 * * * *` (`IMMOBILITY_CRON_INTERVAL`) sobre todos los estudios activos, con mutex single-flight `immobilityCheckRunning` para evitar overlaps. **Por qué cada 5 min**: necesario para detectar a tiempo la alerta `zone_deviation`.

### Zone Deviation Detection (solo Ornitela)
Para estudios con `ornitelaEnabled=true`, el detector calcula un radio dinámico por animal desde el centroide y el percentil 95 de distancias de los GPS de los últimos 30 días (mínimo 5 km; animales con <7 días de histórico se excluyen) con `@turf/turf`. Si el último GPS está fuera del radio, carga el ACC de las últimas 2 h y promedia `|yAcceleration|`: actividad >150 → `warning`, <30 → `critical`, sin datos ACC → `warning`. Persiste como `zone_deviation` (color `#a855f7`, severidad default `warning`) en `detected_events` con dedup 24h, guardando en `metadata jsonb` `{ km_outside, dynamic_radius_km, centroid_lat, centroid_lng, acc_activity_y, acc_samples }`. Auto-resolución: animales que vuelven dentro del radio se marcan `resolvedStatus=true`. Las alertas críticas se incluyen en `newCriticalAlerts` y en el email agregado (columna "Km fuera de zona"). UI en `/immobility`: tarjeta morada con tabla y marcadores morados en el mapa.

### Post-Sync Alert Trigger
Tras cada sync de Movebank que persista nuevos GPS/ACC en `cached_*_events` se dispara `analyzeImmobility(studyId)` en background (`triggerImmobilityAnalysisInBackground`, vía `setImmediate`, fire-and-forget) para evaluar `mortality`, `no_transmission` y `zone_deviation` con la misma lógica del cron. Hooks: (a) cron `runEventDetection` (un Set `studiesWithNewData` agrega studyIds tras cada `insertCachedGpsEvents`/`insertCachedAccEvents`, dispara una vez por estudio al terminar), y (b) `POST /api/studies/:id/backfill` SSE (dispara al cierre si `totalGps>0 || totalAcc>0`). El sync no se ralentiza (desacople `setImmediate`, errores logueados sin propagar). La dedupe 24h evita duplicados con el cron de inmovilidad.

### Alerting System
Notificaciones automáticas por email para eventos críticos, inmovilidad y monitorización de emisión, con deduplicación.

## Datos: import, caché y calidad

- **Data Synchronization**: integración con Movebank para individuos y deployments, con caché local en PostgreSQL.
- **Data Import**: importación de CSV de varias fuentes (Movebank, Base Lunar, Ornitela) con auto-detección de formato y parsing inteligente. Los individuos importados por CSV reciben `movebankId` negativos únicos para evitar conflictos de unique-constraint. Tras importar se invalida la caché (individuos, conteos GPS, last-positions). Columna "Eventos GPS" en la tabla de individuos vía `GET /api/studies/:id/gps-counts`.
- **Data Caching Strategy**: enfoque cache-first para GPS y acelerómetro, con tracking explícito de rangos y gap-filling para minimizar llamadas a Movebank.
- **GPS Quality Filter (HDOP)**: los CSVs Ornitela incluyen `hdop`. El parser (`server/ornitelaCsvParser.ts`) detecta `findCol("hdop","h_dop","gps_hdop","horizontal_dop")` y lo persiste en `cached_gps_events.hdop` (`doublePrecision`, nullable; Movebank inserta `null`). Constante `HDOP_QUALITY_THRESHOLD=5` en `shared/schema.ts`. **Alertas**: `getLatestCachedGpsEvent` filtra `hdop IS NULL OR hdop <= 5` en SQL para "última posición válida"; `filterHighQualityGps` excluye HDOP>5 de `analyzeImmobility` (mortality/no_transmission) y del radio dinámico de `zone_deviation`. Movebank y otros sin HDOP no se afectan (NULL acepta). **Mapas**: `last-positions.tsx` y `study-visualization.tsx` renderizan puntos con HDOP>5 en gris `#9ca3af` con `dashArray` y opacidad reducida, y muestran "HDOP: x.x (baja calidad)" en el popup. Los puntos NO se eliminan, sólo se diferencian visualmente.
- **Geospatial Analysis Engine**: Turf.js para home range (MCP, kernel density), distancia recorrida y velocidad, con visualización y exportación (KML/GeoJSON).

## Seguridad
- **Credential Security**: cifrado en reposo de credenciales externas sensibles (p. ej. Movebank) con AES-256-GCM. La clave se lee de la variable de entorno `ENCRYPTION_KEY` al arrancar; si falta, el arranque lo reporta. **Por qué**: no almacenar credenciales de terceros en texto plano en la base de datos.

## Programación de tareas (cron)
- **Automated Scheduling**: crons para detección de eventos, chequeos de emisión, análisis de inmovilidad y sync Ornitela.
- **Scheduled Deployment Trigger**: `scripts/cron-sync.mjs` es un script Node standalone pensado para desplegarse como Replit Scheduled Deployment (separado de la web Autoscale). Hace `POST /api/sync-all` con header `X-Sync-Secret` cada 6h, forzando detección de eventos, chequeo de emisión y sync Ornitela con independencia del node-cron in-process (que puede morir cuando Autoscale escala a cero). **`/api/sync-all` NO incluye `immobility_check`**: ese chequeo tiene su propio cron con mutex single-flight (`immobilityCheckRunning`). **Por qué**: evitar overlaps en horas alineadas y emails duplicados de "nuevas" alertas críticas. Cron sugerido: `0 */6 * * *`.

## Variables de entorno
- **`ENCRYPTION_KEY`**: clave AES-256-GCM para cifrar credenciales externas en reposo (ver Seguridad).
- **`ORNITELA_SFTP_PASSWORD`** (secret): password del SFTP de Ornitela.
- **`ORNITELA_SFTP_DISABLED`**: si `=1` deshabilita el SFTP Watcher. **Se mantiene `=1` sólo en desarrollo** para que únicamente producción consuma el feed (ver Integraciones → Ornitela → SFTP Watcher).
- **`ORNITELA_SFTP_HOST/PORT/USER/REMOTE_DIR/POLL_MS`** (opcionales): overrides de conexión SFTP.
- **`ORNITELA_DEFAULT_STUDY_ID`** (opcional): fallback de resolución de estudio para archivos SFTP.
- **`SYNC_URL`** y **`SYNC_SECRET`**: requeridas por `scripts/cron-sync.mjs` (`SYNC_URL` p. ej. `https://wildtrack.replit.app/api/sync-all`).
- **`IMMOBILITY_ALERT_EMAIL`** (opcional): destinatario del email crítico agregado (default `jjiglesias@grefa.org`).
- **`IMMOBILITY_CRON_INTERVAL`**: expresión cron del chequeo de inmovilidad.
